# Website Exposure Scan

## 1. Target 결정

사용자 말에서 대상을 고른다. 묻지 않고 바로 시작한다.

- 주소가 있으면(예: "이 웹사이트 점검해줘 https://example.com") 그 사이트를 점검한다.
- 주소 없이 "우리 홈페이지"라고만 하면 지금 폴더의 배포 설정(netlify.toml, vercel.json, package.json의 homepage)이나 README에서 주소를 찾는다. 못 찾으면 그때 주소만 묻는다.
- 폴더를 주거나 "배포 전에"라고 하면 빌드 결과 폴더(dist, build, out, public 순)를 점검한다.

내 사이트인지 정한다. 지금 폴더가 그 사이트 코드이거나 사용자가 "내 사이트", "우리 사이트"라고 했으면 내 사이트다. 남의 사이트는 누구나 보는 것만 보고 `--own`은 쓰지 않는다.

## 2. Scan 실행

```
python3 <이 스킬 폴더>/scripts/scan.py <주소 또는 폴더>       # 누구나 보는 것만
python3 <이 스킬 폴더>/scripts/scan.py <주소> --own            # 내 사이트일 때
```

탐지 항목:

| 구분 | 항목 |
|---|---|
| 소스 | 작업 메모 주석(대표님 지시, 고객 요청, 날짜, TODO, 테스트), 주석·스크립트 속 휴대폰 번호, 주민번호 형식, 개인 메일, 내부 경로 |
| 비밀키 | OpenAI·Anthropic·Stripe·AWS·GitHub·Slack 키, Supabase service_role·secret 키(키 안의 역할을 읽어 공개용 anon 키와 구분), 비밀번호처럼 보이는 값 |
| 빌드 | 소스맵(.map) 공개 여부와 그 안의 원본 코드, 오래된 jQuery·Bootstrap·AngularJS·Lodash |
| 전송 | HTTPS 여부, HTTP로 열릴 때 HTTPS로 넘어가는지, 혼합 콘텐츠 |
| 헤더 | HSTS, CSP, X-Content-Type-Options, Referrer-Policy, 클릭재킹 방지, 로그인 쿠키의 Secure·HttpOnly·SameSite |
| 개인정보보호법 | 연락처를 받는 폼에 수집·이용 동의 문구가 있는지(제15조), 처리방침 링크가 있는지(제30조), 방문자 정보를 보내는 외부 서비스 목록 |
| 공개 파일 | robots.txt에 적힌 관리자 주소 |
| `--own`만 | .env·.git 같은 설정 파일이 열리는지, 사이트의 공개 키로 Supabase 표가 로그인 없이 읽히는지(표마다 1줄, 열 이름만 보고), Firebase Realtime Database가 열려 있는지 |

AI 빌더(러버블, 볼트, v0 등)로 만든 사이트는 내용이 JS에 있어서 JS까지 받는다(같은 사이트 20쪽, JS·CSS 40개).

스크립트가 못 받는 사이트(봇 차단, 로그인 필요)는 그 사실을 알리고, 브라우저에서 소스 보기 → 전체 선택 → 복사해 붙여 달라고 한 뒤 같은 기준으로 읽는다.

결과를 그대로 넘기지 말고 거른다.
- '확인' 등급(화면에 보이는 연락처, 개인 메일, 지도용 구글 키)은 문맥을 보고 일부러 공개한 거면 빼거나 "괜찮음"으로 적는다.
- 스크립트가 못 보는 것도 훑는다: `display:none`으로 숨긴 문장, AI에게 준 지시문 같은 문장.

## 3. Report

쉬운 말로 쓴다.

1. 한 줄 결론: "급히 고칠 것 N개, 고치면 좋은 것 N개"
2. 비밀키가 나왔으면 맨 위에 키 교체 순서(새 키 발급 → 사이트에 넣기 → 확인 → 옛 키 삭제, 모르는 사용 기록이 있으면 옛 키부터 삭제).
3. 표: 등급 / 위치(파일:줄) / 찾은 내용 / 왜 문제인지 / 누가 고치나(스킬이 고침, 콘솔에서 직접). 번호 뒷자리와 키는 가리고, 사람 이름은 성만(박○○), 주소는 시·구까지만.
4. 콘솔에서 직접 해야 하는 것은 `references/fixes.md` D절의 순서를 그대로 적는다(Supabase: Advisors → Security Advisor → Database → Policies → Enable RLS).
5. 이번 점검으로 알 수 없는 것 한 줄(남의 사이트면 DB 권한, 로그인 뒤 화면, 서버 코드).

## 4. Remediation ("고쳐줘", "지워줘" 요청 시에만)

`references/fixes.md`를 따른다.

- 주소로 점검했으면 고칠 코드는 사용자 컴퓨터의 프로젝트 폴더에 있다. 지금 폴더가 그 사이트 코드인지 확인하고, 아니면 위치를 묻는다.
- 원본을 `원본-백업/`에 복사한 뒤 원본 코드(src)를 고친다.
- 스킬이 고치는 것: 메모·테스트 데이터 삭제, 소스맵 끄기, 보안 헤더 설정 파일, 폼 동의 문구와 체크박스, 처리방침 링크와 초안, 라이브러리 버전, http 주소, robots.txt.
- 사람이 하는 것(순서만 안내): 키 재발급, Supabase RLS·정책, Firebase 규칙, 호스팅 HTTPS 설정, 관리자 비밀번호.
- 고친 뒤 빌드 폴더를 다시 점검해 0개인지, 화면이 그대로인지 확인한다.
- 배포는 하지 않는다. 배포 뒤 `--own`으로 한 번 더 점검하라고 안내한다.

## 5. 재발 방지

보고 끝에 한 줄: "AI에게 사이트를 맡길 때 '작업 메모와 테스트 데이터는 코드에 남기지 말고, 키는 화면 코드에 넣지 마'라고 처음에 말해 두면 같은 일이 줄어요."

## 범위 밖

- 남의 사이트에 `--own`, 관리자 주소 접속, 로그인 시도, 찾은 키 사용을 하지 않는다. 문제를 찾으면 그 회사에 알리라고만 안내한다.
- 찾은 개인정보와 키 원문을 보고서나 파일에 적지 않는다.
- 로그인 뒤 화면, 서버 코드, 결제 로직, 침투 테스트는 이 스킬 범위 밖이다. 필요하면 개발자 점검을 권한다.
